### 2026-08-06 통역 역할 계약 확정 (설계 검토 — 연구자·AI 도구(Fable·Codex))

495 배치의 통역 표시 117건이 직접 대화 장면으로 생성된 결함(자동검사 미검출)을 계기로,
번역·통역의 학습자 역할을 다음처럼 확정한다. **번역 셀과 번역 프롬프트는 불변이다.**

**역할 비대칭 (의도된 설계 — 결함 아님):**

| 모드 | 학습자 역할 | P·D·R 준거 |
|---|---|---|
| 번역 | 1인칭 발신자 관점의 번역 수행자 (자기 발신 상황의 원문 제약형 번역) | 학습자 ↔ 상대 |
| 통역 | 별도의 통역사 C | 원발화자 A ↔ 청자 B |

**통역 셀 역할 구조 (자연어 검사보다 먼저 구조로 고정):**

```text
A = 원발화자 (source speaker)      — 화행 목적의 소유자
B = 목표 청자 (target addressee)
C = 학습자 통역사 (interpreter only) — 언어적 실현자
pragmatic relation = A ↔ B
```

**구조값으로의 고정 (`context_spec.interpreter_role_contract`):** 위 역할 구조는 상황문의
자연어 표현에 맡기지 않고, 통역 셀에 한해 서버가 다음 필드를 주입해 고정한다.

```ts
interpreter_role_contract: {
  source_speaker:     "A",        // 원발화자
  target_addressee:   "B",        // 목표 청자
  learner_interpreter:"C",        // 학습자 통역사
  pdr_relation:       "A_to_B",   // P·D·R 준거
}
```

네 값은 모두 고정 리터럴이며 다른 값을 가질 수 없다. 번역 셀과 이 계약 이전의 기존
코어에는 이 필드가 없어도 된다(optional). 역할 비대칭이 문장 표현이 아니라 **데이터
구조로** 보장된다는 뜻이며, 자연어 검사는 그 위에 얹히는 2차 방어선이다.

**핵심 문장 (정본):** 통역 셀의 P·D·R은 원발화자 A와 청자 B의 관계를 나타낸다.
학습자 통역사 C는 이 관계의 당사자나 화행 목적의 소유자가 아니며, P·D·R을 근거로
A의 발화를 자의적으로 개선하는 것이 아니라 A의 의미·의도·화용적 힘을 B에게
기능적으로 등가하게 재현한다.

**등가 재현 ≠ 축자역:** 화용적 힘을 목표어로 등가하게 실현하기 위한 **형식 조정은
필수(허용)** 이고, A의 힘·태도·화행 목적의 **변경은 불허**다. 통역 셀에서 학습자의
화용 판단이 놓이는 자리는 이 등가 실현 수단의 선택이다.

**통역 셀 hard fail 조건:**

1. A 또는 B를 `학습자`라고 부름
2. 학습자가 원발화의 화행을 직접 수행함 (`학습자가 직접 요청·사과·불만을 말한다`)
3. 학습자가 목표 청자 역할을 겸함 (감사·사과 등을 받는 당사자)
4. 자기 발화를 자기가 통역함
5. P·D·R을 학습자와 B(또는 학습자와 A)의 관계로 계산함

**서술·문체 규칙:** 상황문은 학습자(통역사) 관점으로 서술하고, 원발화자 A의
1인칭(`저는`·`나는`) 서술을 금지한다. `직접`은 3단 처리 — hard fail(`학습자가 직접
[화행]한다`, `통역 없이 직접 대화한다`) / 경고(`A와 B가 직접 협의한다`류 모호 표현) /
허용(`학습자가 현장에서 직접 통역한다`). 생성 문체에서는 통역 상황문에 `직접`을
쓰지 않는 것을 기본으로 한다.

**검사 층위:** 동사 목록 정규식은 경고 보조 장치다(`듣는다` 자체는 금칙어가 아니다 —
원발화를 듣는 것은 통역사의 본질 행위이고, 화행의 수신 당사자가 되는 것이 결함이다).
결함 판정은 `누가 어떤 화행을 누구에게 하는가`의 논항 구조로 하며, 최종 의미 정합성은
카나리 사람 검수로 확인한다.

**규칙 대응 (저장 전 자동검사):**

| 규칙 | 층위 | 조건 |
|---|---|---|
| R25 | fail | 신규 통역 코어의 `context_spec`에 A/B/C 및 P·D·R=A↔B 역할 계약이 없음 |
| R16 | fail | 통역 셀인데 이중언어 화자·통역 개입 장면이 불명확함 (위 hard fail 5조건) |
| R16 | warning | 통역 역할에 사람 확인이 필요한 경계 사례 |

R16은 **확정 위반은 fail, 판단이 필요한 경계 사례는 warning**으로 2단 운용한다.
warning은 저장을 막지 않고 검수 큐에 표시한다. R25는 구조값 부재를 막으므로
자연어 검사(R16)가 통과하더라도 역할 계약이 없으면 저장되지 않는다.

PRAGMA는 교육 우선형 학습 플랫폼이며, 수업 과정에서 연구 가능한 자료를 남긴다. 생성·평가·저장 계약은 교육 경험을 검사 도구처럼 축소하기 위한 장치가 아니라 다음을 보장하기 위한 기술 계약이다.

- AI 생성물이 사람 검수 없이 학습자에게 공개되지 않는다.
- 상황 적절성, 의미 충실성, 문법·형식 문제를 서로 섞지 않는다.
- 생성물과 학습자 수행의 버전·출처·변경 이력을 식별할 수 있다.
- 현재 자료만으로 교육 효과나 실제 상호작용 능력을 인과적으로 주장하지 않는다.

허용되는 제품·논문 설명은 다음 범위다.

> 한·중 통번역 상황에서 맥락 단서를 해석하고, 화행별 핵심 특징을 판단·조절하여 표현으로 산출하는 능력을 지원하고 기록한다.

핵심 구성개념은 `상황 기반 화용적 의사결정 및 표현 조절 능력`이다. `전반적 화용 능력`이나 실제 상호작용 능력 전체를 측정한다고 주장하지 않는다.

**정체성 문장 (2026-08-06 확정 — 계약·학습자 구조·논문 공통 기준):**

> 1. PRAGMA는 학습자가 상황에 맞는 외국어 화행을 자유롭게 만들어 내도록 하는 도구가
>    아니라, 주어진 원발화의 의미와 의도를 보존하면서 특정 수신자와 상황에 적절한
>    목표어 표현을 판단·산출·수정하도록 지원하는 통번역 학습 워크플로우이다.
> 2. 번역 모드에서 학습자는 발신자 관점에서 주어진 원문을 읽고 목표어 텍스트로
>    옮기고(자기 발신 상황의 원문 제약형 번역), 통역 모드에서 학습자는 별도의
>    통역사로서 원발화자 A의 음성을 듣고 청자 B에게 목표어 발화로 옮긴다. 역할은
>    모드마다 다르지만, 두 모드 모두 원문 제약과 상황 제약을 동시에 만족해야 한다.

일반 L2 산출 교육과의 경계는 **원문 제약**이다 — "이 상황에서 무엇을 말할까"가 아니라
"이 원발화를 어떻게 옮길까"를 묻는다.

세부 정체성은 `docs/research/PRAGMA_PRODUCT_RESEARCH_IDENTITY_2026-07-28.md`를 따른다.

- 코어에는 MPJ 문항과 DCT 참고안이 없다.
- 495 본 배치는 코어만 생성한다. 495개를 Full Mission으로 일괄 승격하지 않는다.

### 2.2 Full Mission

- 신규 스키마: `mission_v5` (MPJ 구성은 v4와 동일, DCT 원문만 2~4문장 미니 담화 +
  화용 집중 구간으로 확장 — DEC-20260730-01)
- 런타임 피드백 schema는 `feedback_v1`을 유지한다.
- 현행 미션·피드백 `prompt_version` 문자열은 promptSnapshot·Prompt Harness가 정본이다.
  이 문서에 버전 문자열을 복사해 두지 않는다.
- 코어를 선택해 개별 승격하며, 생성 직후 상태는 `generated`다.
- `mission_v1/v2`는 legacy MPJ5, `mission_v3`(2026-07-28 MPJ4 기준선)·`mission_v4`는 열람·회귀 호환용으로 보존한다.
- 기존 v1~v4를 v5로 백필하거나 신규 v5와 같은 생성 계열로 취급하지 않는다.

### 2.3 수행 로그

- 학습자 수행은 기존 `learner_mission_logs` 계열을 사용한다.
- 최초 산출, 제공된 피드백, 수정 산출, 완료 상태와 미션 식별자를 연결한다.
- MPJ 응답은 기존 `context_judgment` JSONB에 `mpj_response_v1` 봉투로 저장한다. 별도 DB 컬럼은 추가하지 않는다.
- 봉투에는 `mission_schema_version`, 문항별 선택 trace, 선택적 `production_support`와 `learner_dissent`를 넣는다.
- Scale4는 4점 원응답을 남기되 적절/부적절 방향만 정오 판단에 사용한다. FixChoice는 최초 Judge3 대역과 선택한 교정안 위치를 함께 남긴다. Reason은 주원인 선택만 남기며 v4 이후 확신도는 생성·노출·저장하지 않는다.
- MultiJudge는 후보별 Judge3를 반복하지 않고 `best_candidate_index`와 `worst_candidate_index`만 남긴다. 번역의 내용 어휘 힌트는 열람 여부와 최초 열람 시각을 `production_support`에 비채점 trace로 남기며, 통역에는 힌트 trace를 만들지 않는다.
- 이 trace는 응답 재구성과 문항 품질 점검을 위한 비채점 기록이다. AI 참고 판정과의 일치 여부를 학습자 점수로 자동 환산하지 않는다.
- 로그가 존재한다는 이유만으로 연구 이용 동의가 성립하지 않는다.
- 이후 새 로그 필드나 분석 의미 변경은 DB 스키마와 연구 주장 범위를 먼저 보고한다.

## 3. 생성 조건과 표본 층위

### 3.1 연구 구인행렬

```text
speech_act 9 × P 3 × D 3 × R 3 = 243셀
```

- `P`: 상대적 권력
- `D`: 사회적 거리
- `R`: 해당 화행의 상황 부담

P·D·R은 상황 적절성 판단의 조건이다. 직접성과 공손성을 하나의 축으로 합치지 않는다.

### 3.2 전달 커버리지

```text
speech_act 9 × learner_level 3 × task_mode 2 = 54셀
```

- `learner_level`: 입문·중급·고급의 교육 지원 수준
- `task_mode`: `translation | stt_interpreting`

54셀은 교육용 전달 커버리지이며 243셀과 같은 연구 구인행렬이 아니다. PRAGMA 수준을 CEFR·ACTFL 등급에 직접 대응시키지 않는다.

### 3.3 편성·사건 메타

- `domain`: 일상·학업·직장
- `theme`: 강좌 편성 영역
- `topic`: 구체적 사건 시드
- `industry`: 직장 장면의 분야 메타
- `context_spec`: P·D·R과 사건 시드의 내부 호환성 해결층

이 값들은 필요하지만 P·D·R과 같은 독립 화용 구인으로 과장하지 않는다.

## 4. 화행과 target feature

교육용 화행은 9종이다.

- 요청
- 거절
- 감사
- 사과
- 제안
- 초대
- 반대
- 칭찬
- 직접 불만

9화행 모두 사람이 작성한 기본 `target_feature`를 가진다. 칭찬하기와 칭찬 대응은 교육적으로 구분된 feature로 보존하되, 현재 `compliment` 코어의 자동 승격 기본값은 칭찬하기 feature다.

계약 원칙:

- `targetFeatures.ts`의 코드·version·band schema가 실행 정본이다.
- AI가 target feature, band code, learner label을 임의로 만들지 않는다.
- 모든 band는 인간 캘리브레이션 전 `proposed` 지위다.
- 표현 자원은 가능한 실현 수단이지 고정 정답 목록이 아니다.
- 한 화행에 복수의 기능적 head와 supportive move가 함께 나타날 수 있다.
- 상황 적절성, 직접성·공손성, 화행별 target feature를 분리해 해석한다.

### 4.1 `usable_facts` 폐쇄 목록

명제적 supportive move는 코어의 `usable_facts` 또는 출발문에 있는 사실만 사용할 수 있다.

- 최대 8개
- 목록 밖의 이유, 대안, 수리, 보상, 재발 방지 약속, 새 일정 추가 금지
- 사실의 유무를 MPJ 정답 단서로 사용 금지
- 관습화된 사과·인사, 완화어, 호칭 같은 비명제적 자원은 폐쇄 목록 대상이 아니다.

## 5. 코어 생성 계약

### 5.1 모델과 응답 형식

- 모델: `gpt-4.1-mini`
- **연구 콘텐츠(코어·미션·비평)에는 모델 교체 폴백이 없다** — 실패를 숨기고 다른 모델로
  강등하지 않는다(2026-08-04 제거). 학습자 런타임 피드백만 가용성 폴백(`gpt-4o-mini`)을
  유지하며, 폴백 발생은 호출 원장에 구분 기록된다.
- API: Chat Completions
- 코어 출력: strict Structured Outputs
- `strict: true`
- `additionalProperties: false`

필수 모델 출력 5필드:

```text
situation_ko
relation_ko
source_text
preceding_turn
brief_note_ko
```

출력 키와 DB 저장 구조는 strict 적용 전과 같다. strict schema 적용은 출력 형식 강화이며, 내용 타당성을 자동 보장하지 않는다.

### 5.2 코어 생성 계열

현재 코어 표면 해시 값은 **Prompt Harness와 ACTIVE_HANDOFF가 정본**이다. 이 문서에
해시 값을 복사해 두지 않는다. 해시에는 다음이 포함된다.

- system/user 프롬프트 템플릿
- 서버 주입 카탈로그와 조립 규칙
- 모델과 폴백 모델
- temperature
- response format
- strict JSON Schema 전문

셀별 화행·수준·도메인·P/D/R 값은 각 행의 구조화 필드로 저장하며 표면 해시에 넣지 않는다.

해시가 바뀌면 이전 계열 생성물과 같은 동결 집합으로 섞지 않는다.

### 5.3 코어 자동검사

- 결정론 검사: 스키마·축·모드·인접쌍·topic·산업 등 저장 전 규칙
- 보조 AI 비평: `core_quality_v5`, 15축
- 사람 눈검사: 최종 콘텐츠 판단

AI 비평의 `pass`는 사람 검수나 내용 타당화를 대체하지 않는다.

## 6. Full Mission 생성 계약

### 6.1 현행 mission_v5 (MPJ 구성은 v4와 동일, DCT 원문 = 2~4문장 미니 담화)

```text
1. Scale4
   매우 적절 / 다소 적절 / 다소 부적절 / 매우 부적절
   → 적절/부적절 방향이 맞으면 인정
   → reference_scale_code와의 정도 차이는 참고·수업 토론 자료

2. Judge3 + FixChoice 4
   과소·적정·과잉 판단 1회
   → 수정안 4개 중 적절한 서로 다른 전략 2개 복수 선택

3. Reason 3
   “이 표현은 이 상황에 맞지 않습니다”를 전제
   → 가장 큰 이유 1개 선택
   → Judge3 반복 없음, 확신도 없음

4. MultiJudge 5
   과소 2 + 적정 전략 2 + 과잉 1
   → 한 화면에서 BEST 1개와 WORST 1개 선택
   → 제출 뒤 다섯 초안의 참고 대역 공개

5. DCT
   번역 또는 통역 산출 → 피드백
   → 세 층 모두 통과하면 현재 표현으로 완료 또는 선택적 재표현
   → 수정이 필요하면 원문과 다른 수정안을 작성한 뒤 완료
```

- `scale4`는 독립 첫인상 문항이다. `accepted_scale_codes`는 같은 방향의 두 코드이고, `reference_scale_code`는 그 안의 대표 정도 하나다.
- Scale4는 각 target feature 카탈로그의 `counter_rule_ko`가 경계하는 소박한 규칙에 대한 반례를 우선 배치한다. 특정 PDR에서는 직접성·강도·명료성·책임 범위 등 해당 자원의 다른 대역이 적절할 수 있음을 보여 주어, 더 간접적·길거나 강한 표현을 자동 상향하는 편향을 막는다.
- `fix_choice`가 Judge3와 교정을 한 문항에 결합하되 UI에서는 Judge 제출 후 교정안을 순차 공개한다.
- `reason`은 이유 3개와 단일 `accepted_reason_id`를 가진다.
- `multi_judge` 후보 수는 모든 수준에서 5개로 고정한다. 후보마다 Judge3를 반복하지 않고, 다섯 후보를 동시에 보면서 각 행의 BEST/WORST 태그로 하나씩 고른다.
- 선택지 수를 수준 난이도로 사용하지 않는다. 난이도는 장면과 표현의 미묘함으로 조절한다.
- DCT는 MPJ와 같은 `mission_id`, attempt와 `target_feature`에 속한다. MPJ 완료만으로 미션 완료 처리하지 않는다.
- 현행 v5의 `production_task.mode`는 번역 또는 통역 하나다. 번역·통역 연계는 과목 설정, 주 수행/보조 수행 구분, companion 로그 계약을 먼저 설계한 뒤 별도 버전에서 추가한다.

### 6.2 Reason·맥락·전이 게이트

Reason 단일 선택은 다음 조건에서만 허용한다.

- 문항마다 하나의 주된 target-feature 원인이 명확하다.
- 이유 3개는 `primary` 1, `pragmatic_misconception` 1, `meaning_grammar_context` 1이다.
- 정답은 `primary` 하나뿐이다.
- 오답도 target에 실제로 보이는 표현이나 인접한 화용 쟁점을 근거로 한 그럴듯한 설명이어야 하며, 황당한 문법 주장이나 상황과 무관한 절대 규칙으로 쉽게 제거할 수 있어서는 안 된다.
- primary의 위치와 ID를 고정하지 않고 선택지 순서를 섞는다.
- 두 이유가 동등하게 방어 가능하면 생성 실패 또는 AI 품질검사 fail이다.
- 복수 head와 supportive move 자체를 금지하지 않는다. 다만 이 문항의 가장 큰 판정 원인은 하나여야 한다.

P·D·R은 원시 코드를 학생에게 보여 주지 않고, 서로 이어진 2~3문장 상황에서 권한·접촉 이력·실제 부담의 구체적 근거로 추론 가능해야 한다.

- `situation_ko`는 역할 메타데이터를 나열하지 않고, 원문 화행의 주체가 누구에게 무엇을 하려는지 먼저 드러낸다. 번역 셀은 학습자 1인칭 과업으로 서술할 수 있지만, 통역 셀은 원발화자 A와 청자 B 사이에서 학습자가 별도 통역사로 개입한다고 서술한다. 다음 문장에 접촉 이력과 상대가 감수할 실제 부담을 자연스럽게 잇는다. 기록 목적·즉시 반응 여부 같은 매체 속성을 연구 설명처럼 풀어 쓰거나, 상대의 권리·선택권·의무와 답안에 포함할 표현 자원 같은 평가 기준을 학생용 상황문에 노출하지 않는다. 이 조건은 내부 `context_spec`·P·D·R·target feature에만 보존한다.
- AI 품질검사의 `scene_underspecified`도 같은 경계를 사용한다. 상대·용건이 없거나 관계·접촉 이력과 실제 부담이 모두 빠져 P·D·R 판단이 실제로 갈릴 때만 보고하며, 문장이 짧거나 기록 목적·즉시 반응 여부가 설명되지 않았다는 이유만으로 결함을 만들지 않는다.
- `relation_ko`의 학습자 표시값은 하나의 `상대` 칩에 들어갈 상대의 역할과 학습자와의 관계를 자연스럽게 합친다. 별도 `상대`·`관계` 칩으로 분리하지 않으며, 두 역할의 병렬 나열, 화자 역할, `A → B`, P·D·R 코드·라벨은 표시값에 넣지 않는다.
- 현행 미션의 네 MPJ에는 모두 target-language `preceding_turn`을 둔다. 이 발화는 상대와 관계가 있는 대화 맥락을 보여 주되, 해당 문항의 정답 표현이나 원문을 그대로 제공하지 않는다.
- legacy 행에 화자와 상대가 함께 저장돼 있으면 러너 UI에서 오른쪽 상대 정보만 추출한다. 저장 원문과 관리자 검수 화면은 바꾸지 않는다.

주간 미션의 맥락 배치는 `앵커+대비`다.

- Scale4: 소박한 규칙의 반례가 실제로 적절해지는 대비 PDR
- Judge3+FixChoice와 Reason: DCT와 같은 앵커 PDR, 서로 다른 사건
- MultiJudge: 앵커 P/D/R 중 정확히 한 축만 바꾼 대비 상황
- DCT: 같은 앵커 PDR의 새 사건으로 근접 전이

주간 DCT만으로 광범위한 전이를 주장하지 않는다. 학기 전체 PDR 배치표에서 주차별 조건을 순환하고, 중간·기말 통합 과제에는 P·D·R 중 하나 이상이 달라지는 전이 문항을 둔다. 배치 자체는 전이 학습의 기회이며, 실제 전이는 수행 자료로 검증한다.

### 6.3 미션 모델과 형식

- 미션 승격 모델: `gpt-4o`
- 현재 미션 출력: JSON mode
- 미션 strict JSON Schema: 미구현
- 생성 후 결정론 검사
- 실패 시 전체 미션 재생성, 최대 2회
- 필드 단위 repair와 outline 파이프라인은 사용하지 않는다.

### 6.4 R5 길이 단서 판정 해석 (2026-07-31 확정)

R5는 `multi_judge` 후보의 길이가 목표 화용 판단을 우회하는 응답 단서로 작동하는 것을 통제한다. 판정 수준은 다음과 같이 해석한다.

- **hard fail(저장 차단)**: 모든 non-within 후보의 길이가 within 후보 구간의 한쪽 밖에만 분포하는 완전 분리. 과소(짧음)–적정(중간)–과잉(긺)처럼 부적절안이 within 구간 양쪽에 나뉘는 배열은 fail이 아니다. 구현 기준은 `checkMultiJudgeLength`의 `separable` 조건이며, 이 서술이 `PRAGMA_생성계약_v1_2026-07-23.md`의 "완전 단조 = 길이순 정답키" 표현보다 우선한다 — 그 표현은 실제 차단 범위보다 넓다.
- **warning(인간 검수 신호)**: 과잉안 유일 최장, 과소안 최단 집중, 최장/최단 비율 3 초과. 저장을 막지 않으며 조립 단계 눈검사의 대상이다.

2026-07-31의 9화행 파일럿에서 B2 프롬프트 보강(대역과 길이를 별개 축으로 명시하고 탈상관 조합을 요구)은 미션 생성 성공률과 일부 길이 구간 중첩을 개선했다. 다만 화행별 1표본이므로 길이 단서 문제가 일반적으로 해소되었다고 보지 않는다.

길이가 일부 target feature와 자연스럽게 관련될 수 있다는 사실과, 길이가 응답 단서로 작동한다는 사실은 동시에 참일 수 있다. 채점상 within이 아닌 모든 후보가 유효한 WORST이므로(`mpjSummary`의 방향 일치 판정), 학습자가 목표 화용 판단 없이 길이만으로 유효한 BEST/WORST를 식별하거나 선택지를 현저히 좁힐 수 있다면 수정 대상으로 판정한다. 반복 표본에서도 동일 경향이 지속되면 축별 생성 전략 또는 응답 판정 방식의 분화를 재검토한다(현재는 미도입·유보).

## 7. 평가와 피드백 경계

### 7.1 분리 원칙

피드백은 최소 다음 층을 구분한다.

1. 의미·의도 충실성
2. 명백한 문법·형식 문제
3. 해당 target feature의 상황 적절성

직접성, 공손성, 의미 충실성을 하나의 총점으로 합치지 않는다. 더 길거나 더 완곡한 표현을 자동으로 더 좋은 답으로 판정하지 않는다.

MPJ 4개가 끝나면 별도 학습 단계를 추가하지 않고 기존 handoff에서 실제 응답을 네 개의 한 줄 SUMMARY로 정리한다. 각 줄은 `첫인상 판단 → 판단하고 고쳐보기 → 이유 찾기 → 여러 초안 비교`의 기능과 이번 장면에서 확인한 판단 기준을 연결한다. 성공 문구는 `targetFeatures.ts`의 기능별 `handoff_summary`를 정본으로 사용하며, 요청 화행의 직접성·선택권 문구를 다른 기능에 재사용하지 않는다. 참고 판정과 다른 행만 수업에서 이유를 비교하도록 짧게 안내하며, 정답·오답 성적표나 별도의 일반 흐름 문장은 제시하지 않는다.

학습자 피드백 화면은 `내 답 → 의미 전달·문법 정확성·상황 적절성 판정 → 다음 행동`만 우선 노출한다. 세 판정은 상태 아이콘과 `통과/수정 필요`로 결과를 분명히 하고, 통과한 층에는 구체적인 긍정 문구를 제공한다. 세 층이 모두 통과하면 수정을 강제하지 않고 `이 표현으로 완료`를 주 행동으로 제공하며, `다른 표현도 시도해보기`는 선택 행동으로 둔다. 수정이 필요한 경우에만 `한 번 다듬어보기`로 연결하고, 원문과 실질적으로 다른 수정안을 작성해야 완료할 수 있다. 앞뒤 공백만 다른 답은 수정으로 인정하지 않되 내부 공백은 언어별 의미 가능성을 고려해 자동 정규화하지 않는다. 여러 층이 동시에 실패한 한 번의 수정 과업은 `의미 전달 → 이번 미션의 목표 화용 축 → 문법 정확성` 순서로 최종 수정 목표를 정한다. 세 층의 독립 판정과 상세 피드백은 그대로 보존한다. 이는 점수나 절대 정답 선언이 아니며 AI 참고 판정 고지는 유지한다. 판정 근거 전문은 관리자 검수·로그에 남기며 학습자에게 반복해 읽히지 않는다. 공통 피드백 프롬프트는 요청 화행을 기본값으로 삼지 않고, 의미층에서는 사실·조건·핵심 화행 내용만 확인하며 강도·완화·선택권·명료성·범위 등 목표 화용 자원의 변화는 화용층에서 판정한다. 다듬기 화면은 판정 결과에서 도출한 한 줄 수정 행동을 제시하고, 완료 화면은 수정 전·후, 바뀐 부분, 해당 답안에 맞춘 한 줄 조언, 저장 상태와 다음 행동만 남긴다. 판정 결과가 없을 때만 일반 원칙 한 줄을 대체 문구로 사용한다.

DCT 산출 화면에서는 장면 설명과 실제 수행 도구를 한 카드에 붙이지 않는다. 번역은 `지금, 직접 번역할 장면`과 메신저 입력 화면을 분리하고, 통역은 장면 카드와 듣기·녹음 프레임을 분리한다. 두 장면 카드는 고정 최소 높이를 두지 않고 같은 패딩·행간·문장 간격을 사용해 내용 길이에 맞게 줄어든다. 한→중 번역에는 산출을 막는 비화용적 내용 어휘·고유명사·전문용어만 정확히 2개 제공하며, 기본 접힘 상태에서 학습자가 요청할 때 한 줄 패널로 펼친다. target feature의 완화 표지, 문장 구조와 완성 답안은 힌트로 제공하지 않는다. 통역에는 첫 수행과 재도전을 포함해 힌트를 제공하지 않는다.

### 7.2 사람 검수

상태 흐름:

```text
core-only
→ generated
→ AI/결정론 검사
→ 사람 검수
→ reviewed
```

- 일반 학습자 공개 최소 조건: `mission_status='reviewed'`
- 연구 분반에서 band를 측정 주장에 사용할 경우: `reviewed`와 별도의 인간 캘리브레이션 상태가 필요하다.
- `generated`는 생성 성공이지 교육적 승인 상태가 아니다.

## 8. provenance와 재현성

코어와 미션은 최소 다음을 식별할 수 있어야 한다.

- model
- provider
- prompt version
- prompt snapshot hash 또는 mission content hash
- generated_at
- generation attempt
- schema version
- language direction

Edge가 계산한 `prompt_snapshot_hash`를 클라이언트가 변형하거나 로컬 코드로 재계산하지 않는다. 프롬프트 정본 화면은 배포 Edge 소스에서 생성된 저장소 스냅샷과 저장 행의 지문을 대조한다.

## 9. 배포·검증 상태는 여기 적지 않는다

Edge 배포 버전, migration 적용 여부, 스모크 결과, 테스트 수, 프롬프트 스냅샷 수·해시는
날짜 종속 사실이다. 이 계약 문서에 적으면 반드시 썩는다.

- 현재 상태의 정본: `docs/handoff/ACTIVE_HANDOFF.md` (최상단 절)
- 시점 고정 증거: `docs/research-trail/` (evidence·dev-log)
- 프롬프트·해시 대조: `/admin/prompt-harness`
- 현행 모든 코어·미션은 조건 LOCK 전 개발·테스트 콘텐츠이며, LOCK 뒤 전량 재생산한다
  (`docs/operations/CONTENT_REFRESH_RUNBOOK.md`).

## 10. 운영 금지와 승인 게이트

- 495/500 대량 배치를 임의 실행하지 않는다.
- core hash 변경 전 영향 범위와 새 생성 계열 분리 방식을 보고한다.
- 생성·평가·저장 계약, DB schema, RLS, prompt hash에 영향이 있으면 먼저 범위를 보고한다.
- migration 적용, Edge 배포, Railway 배포는 사용자 승인 없이 실행하지 않는다.
- `generated`를 `reviewed`로 자동 승격하지 않는다.
- target feature의 학술적 지위를 코드 구현만으로 validated라고 부르지 않는다.
- 라운지 활동은 이 계약의 학습 수행·연구 로그에 포함하지 않는다.
