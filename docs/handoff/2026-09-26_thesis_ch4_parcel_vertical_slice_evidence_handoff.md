## 7. 4.3.5 근거

대상 항: **학습 수행 기록의 저장과 조회**.

1. **논문에서 주장 가능한 사실**: 완료된 수행의 다섯 MJT 응답·최초/최종 번역·실제 AI 피드백·편성 식별자·승인 콘텐츠 해시가 운영 DB에 저장됐다. 별도 학습 기록 화면에서 최초·최종안을 다시 조회했으며 새로고침 후에도 동일했다.
2. **직접 근거 파일 / 코드 / DB / 실행 결과**: [L] 전체 행; S11 저장 성공 알림; S12의 `/learner/records#correction-notes` 최초·수정안과 `새로고침 후 동일 내용 재조회: PASS`; [F] 저장·재조회 및 실행 검증. C06은 `learner_mission_logs` 저장, C07은 저장 행 구성, C08은 본인 완료 기록 조회를 보여 준다. DB에서 피드백·식별자까지 확인한 사실과 기록 UI에서 최초·최종안을 재조회한 사실을 구분한다.
3. **대표 화면에서 보여 줄 장면**: 완료 화면의 최초·최종안과 저장 알림, 이어서 기록 화면의 동일 두 산출. 한 화면만으로 승인·DB 필드 전체를 입증하는 것으로 설명하지 않는다.
4. **핵심 ID·해시·버전**: [L] `id`=§2 log, `attempt_id`=§2 attempt, `mission_id`·`course_id`·`week_no=2`·`assignment_id`, `content_hash`=H, `context_judgment.mission_content_hash`=H, `mission_completed=true`. [A]의 승인 version ID·H와 연결되지만 version ID가 [L]에 직접 저장된 것으로 쓰지 않는다.
5. **주장하면 안 되는 것**: 모든 장애·중복 제출·오프라인 복구·브라우저/기기 변경 복원 검증, 장기 축적 데이터 분석, 학생 학습이력 일반화, 사용자 간 접근 통제 전체 검증. reload 후 기록 조회 성공을 수행 중단 복원 전체 검증으로 확대하지 않는다.
6. **제4장에서 설명할 구현 의미**: 한 번의 수행이 화면에서 사라지지 않고, 승인 콘텐츠·편성·응답·피드백·최종 산출의 연결을 추적할 수 있는 기록으로 남는다는 구현 사실이다.

## 8. 4.5.2 대표 개선 사례 2~3건

선정: 아래 3건. 모두 **수정 전 원문 → 국소 변경 기록 → 최종 감수본 → 승인 v3 → 실제 문항 수행·저장**이 연결된다. 부적절한 번역을 의도적으로 판단·교정 대상으로 남긴 사실과, 콘텐츠 제작상의 보완을 구별한다. 문항 속 부적절 표현이 있었다는 사실 자체를 앱 결함으로 보고하지 않는다.

공통 증거 사슬: 원시 `case-1.before.json` → `case-1.patch.json` → [R] 검토 의견 처리 → `parcel-quality-v2.json`·`parcel-review-finalization.json`의 기존 결과 → [A] v3/H·승인 note → S04/S06/S07 → [L]. `case-1.patch.json`은 작업용 변경 기록이므로 최종 저장 여부는 [A]로 확정한다. 개별 개선마다 독립적인 연구자 클릭 승인 기록이 있는 것으로 쓰지 않는다. 개별 처리의 기록은 [R]·dev-log, 전체 최종 수용의 근거는 사용자의 ‘진행’과 [A] 승인 note다.
