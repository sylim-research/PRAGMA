## 1. 사이드바 — 콘텐츠가 지나는 순서로

메뉴가 만들어진 순서대로 자라 있었다. 재료에 불과한 시나리오 관련 항목이 4개인데
MJT5+DCT1이 조립되는 학습 미션은 1개였고, 이 연구의 차별점인 품질 관리는 그룹조차 없었다.
**메뉴만 보면 이 시스템의 산출물이 시나리오처럼 읽혔다.**

5그룹: `생성 기준·시나리오 재료 → 학습 미션 → 콘텐츠 품질 관리 → 수업 운영 → 학습 기록·연구 자료`

## 2. AI 검토와 교수자 승인을 화면으로 분리

`ProfessorMissionWorkbench`가 `ContentReviewPanel`을 그대로 품고 있어서 **조립 화면에서도
규칙 검사·AI 3단계·최종 승인이 전부 가능했다.** 메뉴는 두 화면인데 하나가 다른 하나를 포함했다.

- `/admin/ai-review` 신설 — 판단 자료 준비만. **승인 절과 버튼이 렌더되지 않는다**
  (`next === "professor" && !handoffHref`)
- 승인은 `/admin/review`에서만. 화면 안에서 `① 교수자 감수` / `② 최종 승인`을 나누고
  「수정 저장은 최종 승인이 아닙니다」를 명시
- 🔴 **화면을 나누되 작업은 나누지 않는다** — 인계 링크(`?scenarioId=`)를 처음부터 넣고
  **단계와 무관하게 항상 노출**한다. 목록 데이터는 나누지 않고 같은 미션·검토 이력을 공유하며
  화면별 상태 보기만 다르다. 이동만으로 승인 상태는 바뀌지 않는다
- 시험 `keeps approving out of the AI review screen` 신설 — AI 쪽에 승인 경로가 생기면 실패한다

## 3. 대시보드 — 워크플로우가 첫 줄

🔴 **표시 오류를 발견해 함께 고쳤다.** 상단 대형 카드가 `227`을 「교수자 감수·승인 대기」라
부르며 44px로 보여주고 있었는데, 실측하니 **227 중 224가 아직 규칙 검사도 안 들어간 상태**였다.
사람을 기다리는 것은 **2건**이다. 「지금 할 일」은 이제 `review.professor`를 읽는다 —
파이프라인 마지막 카드가 이미 쓰던 값이라 새 계산이 없다.

첫 줄은 여섯 구간에 각각 현재 수를 단 워크플로우다.
`시나리오 재료 1,715 · 학습 미션 309 · 품질 관리 227 · 교수자 결정 62 · 수업 편성 67 · 학습 수행 64`

**정적 도식이 아니다.** 숫자가 일의 진행에 따라 움직이므로 지도이면서 현황이다. 정적 그림이면
이틀 만에 눈이 지나간다는 판단으로 살아 있는 수치를 조건으로 걸었다.

- 「미션 재료」 카드는 라이브러리로 이동 — 보유량은 대시보드 KPI가 아니다
- 화면 이름 `운영 대시보드` → **`PRAGMA 운영 워크플로우`**(사이드바·제목 통일).
  ⚠️ `학습 콘텐츠 제작 워크플로우`는 기각 — 뒤의 세 구간(교수자 결정·수업 편성·학습 수행)이
  제작이 아니어서 이름이 범위를 잘라낸다. `PRAGMA 통합 워크플로우`도 기각 — 논문 3.7 도식의
  이름이라 화면이 그것을 쓰면 「도식을 전시했다」로 읽힌다
- **운영 환경 785px** — 스크롤 없이 한 화면

## 4. 화면 간 상호 참조 링크 정리

연구자 원칙: **링크는 대상을 다음 단계로 넘길 때만 정당하다.** 파라미터 없이 메뉴로만 보내는
링크가 쌓이면 사이드바 순서가 무의미해진다.

- 제거 8: 프롬프트↔코퍼스 상호 참조 4, 생성기→라이브러리 3(라이브러리는 `searchParams`를
  아예 안 받아 그 시나리오로 갈 수도 없었다), 원자료→수업자료 1
- 조립 행의 「15주 편성에 사용」·「교과목·주차 수업자료」 제거 — 시나리오를 안 넘기고
  메뉴만 여는 링크가 226행 × 2 = 452개였다
- 유지: 대시보드의 숫자→화면(대시보드의 존재 이유) · 온 길로 돌아가는 링크 · 오류 안내 링크

## 5. 서버 감사 — 근거 수준을 구분해 기록

GPT Pro 지적을 수용해 **「통제의 존재 확인」과 「경로의 통제 입증」을 분리**한다.

| 조건 | 근거 수준 | 실제 근거 |
|---|---|---|
| AI 실행만으로 승인 안 됨 | 코드에 구현 | `approved_at`은 승인 RPC에서만 설정 |
| 수정본에 승인 미승계 | 코드에 구현 | `guard_content_review_scenario`(`:397-402`)가 현재 내용의 `source_hash`로 승인된 기록이 없으면 거부 + `finalize_reviewed_mission`(`:201-206`)이 저장된 검토 대상과 다르면 거부 |
| 승인 대상 = 감수 대상 | 코드에 구현 | 서버가 산출한 `source_hash` 대조(`:95`) + 콘텐츠 동일성 검사 |
| 서버 권한 확인 | 코드에 구현 | RPC 내부 `is_admin()` + edge function 진입부 403 |

🔴 **정정 3건**
1. 앞서 「freeze 트리거가 있으니 이전 승인이 승계되지 않는다」고 썼으나 **논리 비약**이었다.
   그 트리거는 승인 기록의 수정·삭제를 막을 뿐이고, 실제 통제는 위 표의 두 곳이다.
2. 「4단계 완료가 승인 요건」은 **옛 마이그레이션**(`20260827190000`)을 읽은 오류다. 현행은
   `20260906100000_focused_content_review.sql`이고 정책별로 갈린다 — `focused_v1`에서는
   Claude 검토가 **요청했을 때만**, 그것도 findings가 있을 때만 재검토가 필수다. 선택 검토를
   안 돌려도 승인 경로가 열린다. **선택/필수 충돌 없음.**
3. **`is_admin()`은 「관리자」이지 「교수자」가 아니다.** 논문에서 교수자 권한이라 쓰려면
   앱 관리자 역할과 교수자 운영 역할의 대응을 밝혀야 한다.

🔴 **아직 확인하지 않은 것** — 운영 DB에 이 마이그레이션이 적용됐다는 확인 · 「승인된 A를
수정하면 거부된다」의 **실제 실행 결과** · 자동 시험에 이 경로가 있는지.
따라서 지금 말할 수 있는 것은 **「소스 수준에 통제가 구현되어 있다」**까지다.
「화면을 우회해도 뚫리지 않는다」·「논문에 그대로 쓸 수 있다」는 철회한다.

## 남은 것

- **`미션 설계 기준` 화면 미구현** — 사이드바에 넣지 않았다(죽은 링크 방지). 담을 것은 4개로
  좁혔다: 미션 구조(MJT5+DCT1) · 다섯 활동의 목적 · 설계 축 9×3×2×2 · 조립 5단계.
  🔴 **R 규칙 전문은 넣지 않는다** — 실측하니 `R1~R33`이고(29가 아니다) 사람이 읽을 설명이
  없어 33개를 새로 써야 한다. 그것은 「이미 있는 것의 가시화」가 아니라 발명이다.
  전문가 형성평가에서 이 화면의 필요성·명료성·과잉 여부를 확인한 뒤 짓는다.
- **`원자료 분석` 흡수 미착수** — 흡수 전이라 사이드바 항목을 유지했다. `AdminAuthentic`은
  껍데기 55줄이고 이미 `sessionStorage`로 생성기에 넘기므로 값싸다.
- `학급 응답 현황` → `주차별 수업 운영` 흡수 미착수.
- **개별+배치 생성 통합은 후순위** — `AdminGenerator` 1,735줄 + `AdminBatch` 864줄.
  ⚠️ 진입점 통합과 내부 로직 통합은 다른 작업이나, 생성 조건 입력부가 서로 달라 진입점만
  합쳐도 두 UI를 한 화면에 얹어야 한다.
- **메뉴 개편만으로 「사용성이 개선되었다」고 주장하지 않는다** — 사용성 평가를 하지 않았다.
  4.7 전문가 형성평가 전까지는 「지적에 대한 조치」로만 서술한다.
- 관리자 화면은 admin 로그인이 필요해 배포본 확인은 연구자 몫이다.
