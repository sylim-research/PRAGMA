# 「이유 찾기」 문항의 반복 품질 실패 진단 · 2026-09-10

관찰 시점 = 교과목 미션 승격(run `scene_grounding_course_20260910`) 진행 중. 이 문서는 **진단과 선택지**만 담는다. 생성 계약은 고치지 않았다.

## 관찰

미션 품질 검사(`quality_v22_observed_pdr_scene`)가 같은 코드 `primary_reason_ambiguity`를 **4번째 문항(type=reason)의 오답 선택지**에서 반복해 fail로 낸다.

| 미션 | 품질 | 해당 코드 |
|---|---|---|
| w9-1 사과·통역 | pass | — |
| w2-0 요청·번역 | fail | primary_reason_ambiguity @ mpj_items[3].reasons[0] |
| 반대 v2·번역 | pass | — |
| 불만·통역 | pass | — |
| w2-1 요청·통역 | fail | primary_reason_ambiguity + implausible_distractor 2건 |
| w3-0 감사·번역 | fail | primary_reason_ambiguity @ mpj_items[3].reasons[0] |

여섯 건 중 셋이 같은 자리에서 걸렸다. **표본이 작아 오류율로 일반화하지 않는다.** 다만 자리와 코드가 한 곳으로 모이므로 우연으로 보기는 어렵다.

## 계약을 읽고 확인한 것

생성 지시(`generate-scenario/index.ts`)는 오답 두 개를 이렇게 규정한다.

- `r1` = pragmatic_misconception — 「실제 문장 속 단서를 근거로 한 **그럴듯하지만 주원인은 아닌** 화용 해석」
- `r3` = meaning_grammar_context — 「target의 실제 요소를 근거로 한 **그럴듯하지만 주원인은 아닌** 의미·문법·맥락 해석」

품질 검사 ⑨는 이렇게 규정한다.

> accepted_reason_id가 실제로 유일한 **가장 큰 이유**인가. **다른 선택지도 같은 정도로 방어 가능하거나**, primary가 target feature가 아닌 의미·문법 문제라면 fail이다.

즉 생성 쪽은 「그럴듯하게」를 요구하고 검사 쪽은 「같은 정도로 방어 가능하면 실패」로 본다. **두 문장 사이에 빈 구간이 있다** — 생성 지시에는 오답이 정답과 *무엇이 달라야 하는지*가 없다.

## 실패한 세 건을 실제로 읽은 결과

통과한 w9-1과 대비하면 신호가 분명하다.

- **w9-1(통과)**: 정답은 `一点小失误`(책임 축소)를 지목하고, 오답 둘은 모두 **다른 구간**인 `以后我会更小心的`를 지목한다. 겨냥하는 지점이 갈린다.
- **w2-0(실패)**: 정답이 `你就把…`의 직접성을 지목하는데 오답 r1도 같은 문장의 `吧`를 붙들고 같은 축(직접성·명료성)을 말한다. 지점이 겹친다.
- **w2-1(실패)**: 정답과 오답이 문장은 다르나 둘 다 「요청의 직접성·책임 귀속」을 진단한다. 축이 겹친다.
- **w3-0(실패)**: 오답 r3이 「`我在演示前改好了资料`가 자료를 고친 사람을 원문과 다르게 옮겼다」고 하는데, 원문이 「덕분에 발표 전에 자료를 고쳤어요」이므로 **전제가 사실과 다르다**. 그럴듯한 오진이 아니라 근거가 틀린 선택지다.

정리하면 실패는 두 갈래다. ①오답이 정답과 **같은 축**을 진단한다. ②오답의 **전제가 본문과 어긋난다**. 두 경우 모두 검사기 판정이 과하다고 보기 어렵다. 앞서 w2-0을 「설계상 정당한 오답」으로 본 내 판단은 ①에 해당해 재론의 여지가 있다.

## 선택지 — 연구자 판단 필요

이건 코드 이름 오류 같은 결함이 아니라 **생성 계약의 빈 구간**이다. 고치면 모든 미션의 문항 생성 방식이 바뀌므로 승인 사안이다.

- **A. 그대로 두고 건별로 교수자 판정.** 지금 구조 유지. 대신 이유 찾기 문항의 절반가량이 fail을 달고 최종 승인 화면으로 가며, 교수자가 매번 override 사유를 적어야 한다.
- **B. 생성 지시에 오답의 분리 조건 한 줄을 넣는다.** Claude 권고안. 문안 후보:
  > 오답 둘은 정답과 **다른 지점 또는 다른 축**을 지목해야 한다. 정답이 지목한 구간·문제 축을 되풀이하지 않는다. 오답의 전제는 반드시 target 본문에서 확인되는 사실이어야 하며, 본문과 어긋나는 서술을 오답의 근거로 쓰지 않는다.
  - 얻는 것: 반복 실패의 두 원인을 모두 겨냥한다. 통과한 w9-1이 이미 이 형태다.
  - 치르는 것: 미션 생성 프롬프트 버전과 스냅샷 해시가 바뀐다. 이미 만든 미션과 앞으로 만들 미션의 생성 기준이 달라지므로 **콘텐츠 후보 ID를 새로 끊을지**(`_04`) 함께 정해야 한다. 새 ID를 끊으면 `_03`으로 만든 자료가 현행 목록에서 빠지므로 허용 목록 조정이 따른다.
- **C. 검사 ⑨를 느슨하게 한다.** 권고하지 않는다. 실제로 읽어 보니 검사기 지적이 타당한 쪽이었다.

## 별개 관찰 — 검사기의 요약과 판정이 서로 어긋난다

fail을 낸 다섯 건 중 **셋**(w3-0·w4-0·w6-0)은 `summary_ko`가 결함이 없다고 적으면서 fail finding을 함께 냈다.

- w3-0: 「모든 문항이 … 오답도 현실적 경계 사례로 구성되어 있음」 + fail 1건
- w4-0: 「… 오답도 현실적 경계 사례로 제시되어 **결함이 없다**」 + fail 1건
- w6-0: 「… 극단적 오답이나 대역 오류 **없이 설계되었습니다**」 + fail 1건

사전 검토에서도 같은 모양이 나왔다(모든 축이 일치한다고 서술하고 `feasible:false` 반환). **한 응답 안에서 서술과 판정이 어긋나는 것은 이 검사기의 반복되는 습성**으로 보인다.

이건 화면에 그대로 드러난다. `src/components/admin/MissionPreview.tsx`가 `summary_ko`를 교수자 검토 화면에 표시하므로, 교수자는 「결함이 없다」는 문장과 fail 판정을 나란히 보게 된다. 판정을 읽는 데 혼란을 준다.

조치는 하지 않았다. 선택지는 ①그대로 두고 findings를 판정의 정본으로 읽는다 ②요약과 판정이 어긋나면 화면이 요약 대신 findings를 앞세우도록 표시를 고친다(UI 게이트) ③검사 프롬프트에 요약과 판정의 일관성을 요구한다(생성 계약). 어느 쪽이든 연구자 판단이 필요하다.
