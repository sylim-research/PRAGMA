# 2026-09-18 — v5→v6 변환: 3번 문항을 승계하지 않고 집필 자리로 넘김

## 무엇이 문제였나
v5 native는 `judge3`(2번)와 `fix_choice`(3번)가 **같은 자극문**(장면·관계·PDR·원문·번역안)을 쓴다.
변환기가 두 문항을 각각 그대로 옮기다 보니 v6 3번이 2번의 장면과 원문을 되풀이했다.
파일럿 검수(`40c7aa46`)에서 이 반복이 실제로 발견됐다. 승인된 v6 여섯 건은 1·2·3이 모두 다른 장면·PDR·원문이다.

## 바꾼 것
- `src/lib/mission/missionV5ToV6.ts` — 3번 문항의 `situation_ko`·`relation_ko`·`source`·`target`·`corrections`·
  `explanation_ko`를 빈 값으로 두고 gap 7개로 보고한다(`pdr`·`channel`은 v5 fix_choice 값을 자리 표시로 둔다 —
  4번 문항과 같은 방식). 교정안 승계에 쓰던 `correctionOf`는 쓰는 곳이 없어 지웠다.
- `scripts/v6-assemble-candidate.mts` — 집필분 `authored.mjt3`를 3번 문항에 얹는다(`mjt4`와 같은 자리).
  집필분이 없으면 조립기가 「집필분이 비어 있는 자리」로 멈춘다.
- 테스트 — 「교정안을 그대로 옮긴다」 기대를 「3번은 gap으로 보고한다」로 바꾸고, 스키마 통과 검사에 3번 집필분을 채운다.

전체 57건(55슬롯 + 파일럿 2) · 변환 막힘 0 · 장면 재집필 필요 31건. 분포 = 24자리 26건 · 28자리 5건 · 32자리 26건.
3번 문항 한 건당 늘어난 집필 = **경로 7개 = 자리 9개**(교정안 3개를 각각 세면).

## 영향
- 이미 등록된 파일럿 2건(`40c7aa46`·`1d61b487`)은 DB에 있으므로 재조립하지 않는다. 두 건의 3번 문항 반복은
  검수 단계에서 개별 재집필로 처리한다.
- 기존 `*.authored.json` 3개에는 `mjt3`가 없어 그대로 재조립하면 멈춘다 — 의도한 동작이다.
- 규칙·프롬프트·Edge 함수는 건드리지 않았다. 배포 대상 없음.
