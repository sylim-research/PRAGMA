# 2026-09-16 — 교수자 검수 게이트: 결정론적 자동 신호를 묶음 확인으로

교수자 최종 승인 화면에서 규칙 검사의 자동 신호가 AI의 의미 지적과 같은 절차를 요구하던 것을
분리했다. 인간의 최종 결정권은 그대로 두고 반복 입력만 줄였다.

## 발단 — 운영에서 드러난 마찰

연구자가 대표 미션 1번(`630e6459`)을 승인하던 중, 8섹션을 모두 확인하고 승인 근거까지 적었는데도
「교수자 최종 승인」 버튼이 비활성인 상태를 보고했다. 원인은 규칙 검사 신호 1건
(`rule-1 · R32/unattributed_present`)에 교수자 판정과 근거가 저장되지 않아서였다.

그 항목 자체에 이렇게 적혀 있었다.

> 불확실성: 정규식·집계 기반 신호이며 의미 판단이 아닙니다.

즉 시스템이 스스로 의미 판단이 아니라고 표시한 신호에 대해, 교수자에게 10자 이상의 서술을
요구하고 그것이 승인의 선행 조건이었다.

실측: 미션 1건당 최소 인터랙션 14회(8섹션 확인 + 문제 항목당 판정·근거·저장 3회 + 승인 3회),
자유 텍스트 2건. 당시 결정 대기 42건 기준으로 약 590회 클릭과 84개의 서술문이 남아 있었다.

## 원인 — 두 지점

- `src/lib/pragma/contentReviewDomain.ts:60` — 규칙 검사의 `warning`이면 무조건
  `needs_professor: true`. 2026-09-09에 「전부 `needs_professor=false`로 소실됐다」며 켠 것인데,
  그때 의미 지적과 정규식 신호를 구분하지 않았다.
- `supabase/functions/_shared/contentReview.ts:241-247` — 승인 게이트가 `requireClear=true`라
  모든 항목이 `no_change`여야 하고, 그런데도 `rationale_ko`를 10자 이상 요구한다.
  되돌리기 비싼 「수정 필요」·「판단 보류」가 아니라 **통과 판정에 서술이 걸려 있었다.**

## 변경 — frontend only

문제 항목 목록을 두 층으로 나눴다.

**자동 품질 점검 신호 N건** — `rule-*` 접두 + `severity === "warning"` + `needs_professor === true`인
비차단 신호. 요약 한 줄(`R30 ×2 · R32 ×1`), 상세 열람 disclosure, 그리고 **미결 항목만**
「수정 없이 사용 가능」으로 채우는 버튼 1개.

**의미 쟁점 판정 N건** — AI 검토(`openai-*`·`claude-*`·`generation-*`)가 근거를 들어 제기한 항목.
기존과 동일하게 항목별 판정 + 근거 필수.

경계 조건 3가지:

- 묶음 대상 판정은 id만 보지 않는다. `severity`와 `needs_professor`를 함께 본다 —
  계약 위반(`fail`)이 묶음에 섞일 수 없다.
- 이미 결정된 항목(저장분·초안)은 건드리지 않는다. 버튼 문구가 실제 대상 수를 반영하고,
  묶음으로 채운 항목을 손으로 고치면 `mode`가 풀려 개별 판정이 된다.
- 묶음 결정도 `mode: "bulk_signal"`과 전용 근거 문구를 남긴다. 저장 시
  `professor_decisions_by`·`professor_decisions_at`이 함께 기록되므로 교수자·시점·대상 항목이
  그대로 추적된다.

`isBulkEligibleSignal()`과 `BULK_SIGNAL_RATIONALE`은 `_shared/contentReview.ts`에 두어
프런트와 검증 로직이 같은 정의를 쓴다.

## 바꾸지 않은 것

- 8섹션 개별 확인 — 기본 확인 상태로 바꾸지 않았다. 확인하지 않은 섹션이 확인으로 기록되지 않는다.
- 교수자 최종 승인 버튼과 그 선행 조건(모든 항목 `no_change` + 저장 + 승인 근거 + 체크박스).
- DB schema · RPC · Edge Function. SQL의 10자 조건도 그대로 두었다 — 묶음 버튼이 그 조건을
  시스템 문구로 채우므로, 기록에는 「묶음 확인」이라는 결정의 성격이 남는다.
- 기존 승인·판정 기록. 승인된 run의 결정은 SQL이 불변으로 막는다.

## 검증

- `npm run typecheck` · `npm run build` 통과. 단위 테스트 991 pass / 9 skip.
- 새 테스트 7건: 묶음이 차단급 항목을 피하는지, 기존 결정을 덮어쓰지 않는지, AI 지적이 개별
  판정으로 남아 승인을 막는지, 되돌린 항목이 승인을 다시 잠그는지, eligibility predicate 자체.
- localhost 운영 데이터 read-only 확인(쓰기 0): 신호 3건 미션에서 별도 블록·요약 `R30 ×2 · R32 ×1`·
  상세 열람 안의 항목별 판정 select 3개 확인. 신호 0건 미션에서는 블록이 렌더되지 않았다.
  8섹션과 ③ 승인 영역은 그대로였다.
- 한계: 표본 3건 모두 AI 검토 findings가 0건이라 「의미 쟁점 판정」 블록의 실데이터 렌더는
  확인하지 못했다. 기존 개별 판정 보존도 저장이 필요해 화면으로 확인하지 않았다 — 둘 다
  테스트 근거로 둔다.
